# 企业内部邮件：撤回邮件业务逻辑说明

## 1. 目标与边界

邮件撤回用于纠正企业内部误发邮件。它不是“删除发件人已发送记录”，而是针对**同一企业租户内、尚未阅读的收件人副本**发起撤回。

- 仅支持企业内部账户之间的邮件；外部地址、跨租户地址不支持撤回。
- 仅撤回尚未阅读的收件人副本；已阅读副本保留原邮件。
- 撤回不删除发件人“已发送”记录，也不删除审计日志。
- 撤回成功后，收件人不应看到原主题、摘要、正文、附件、星标或任何原邮件操作。
- “撤销发送”是发送延迟期内取消投递的能力，与本功能的“邮件撤回”不同；如后续建设，应作为独立能力处理。

## 2. 角色与界面规则

### 2.1 发件人

发件人可在“已发送”的邮件详情中发起撤回。确认框必须明确展示：

- 收件人总数；
- 可撤回人数（未读）；
- 不可撤回人数（已读）；
- 规则提示：已读收件人仍可查看原邮件。

请求提交后，发件人可看到以下状态：

| 状态 | 含义 | 页面展示 |
|---|---|---|
| 可撤回 | 存在未读的内部收件人 | 可发起撤回 |
| 撤回处理中 | 后端正在处理收件人副本 | 禁止重复发起，提示处理中 |
| 部分撤回 | 仅未读副本撤回成功，仍有已读副本 | 展示成功数、保留数及撤回报告 |
| 已全部撤回 | 全部目标副本均撤回成功 | 展示成功人数及撤回报告 |
| 不可撤回 | 没有符合条件的未读内部副本 | 仅展示原因，不提供撤回操作 |

发件人邮件详情在结果明确后，建议展示：“已从 N 名未读收件人的收件箱中撤回；M 名已读收件人仍可查看原邮件。”

### 2.2 收件人

| 收件人状态 | 收件箱展示 | 点击后展示 |
|---|---|---|
| 未读且撤回成功 | 灰色、不可操作的系统提示记录：“发件人撤回了一封邮件” | 标题“邮件已撤回”；仅展示“正文及附件不可查看” |
| 已读或撤回失败 | 原邮件保持不变 | 保持原有正文、附件与常规操作 |

成功撤回的系统提示记录：

- 不展示原邮件主题、正文摘要、附件名称、附件数量和收件人信息；
- 不允许回复、回复全部、转发、星标、标记未读或查看原邮件；
- 不计入未读数、不进入星标邮件；
- 可保留在原邮件时间位置，便于用户理解邮件为何消失；
- 是否允许用户将“提示记录”移入回收站，可由产品策略确定；原邮件内容始终不可恢复。

## 3. 后端处理流程

1. 发件人提交 `POST /mail/{mailId}/recall`。
2. 服务端校验：当前用户是否为发件人、邮件是否属于内部邮件、是否在允许撤回的保留期、是否已存在处理中任务。
3. 系统为每个收件人副本判定投递状态：`UNREAD`、`READ`、`DELETED`、`EXTERNAL` 等。
4. 对 `UNREAD` 且内部投递成功的副本：原子地将邮件内容副本标记为 `RECALLED`，清除正文与附件访问权，写入最小化系统提示记录。
5. 对 `READ`、`EXTERNAL`、已删除、无权限或状态变化冲突的副本：保留原邮件，并记录失败原因。
6. 汇总成功、失败、处理中数量，更新撤回任务及发件人邮件的汇总状态。
7. 向发件人生成“撤回报告”站内通知；邮件量较大时采用异步任务并支持轮询或推送刷新。

## 4. 建议数据模型

### 4.1 邮件主表 `mail_message`

```text
id, tenant_id, sender_id, subject, body, sent_at,
recall_status, recall_requested_at, recall_completed_at
```

`recall_status` 建议枚举：`NONE`、`PROCESSING`、`PARTIAL`、`FULL`、`UNAVAILABLE`。

### 4.2 收件人副本表 `mail_recipient_message`

```text
id, message_id, recipient_id, delivery_status, read_at,
recalled_at, recall_result, recall_failure_reason
```

`delivery_status`：`UNREAD`、`READ`、`RECALLED`、`DELETED`。

`recall_result`：`PENDING`、`SUCCESS`、`SKIPPED_READ`、`SKIPPED_EXTERNAL`、`FAILED`。

### 4.3 撤回任务及审计表

```text
mail_recall_task: id, message_id, requester_id, status, total_count,
success_count, skipped_read_count, failed_count, requested_at, completed_at

mail_recall_audit: task_id, recipient_message_id, result, reason, created_at
```

审计表至少保留邮件标识、操作者、操作时间、结果、失败原因；不因撤回而抹除原始业务留痕。

## 5. 接口建议

### 发起撤回

`POST /api/internal-mail/messages/{messageId}/recall`

响应示例：

```json
{
  "taskId": "recall_20260915_001",
  "status": "PROCESSING",
  "totalCount": 45,
  "eligibleCount": 7,
  "readCount": 38
}
```

### 查询撤回报告

`GET /api/internal-mail/recall-tasks/{taskId}`

响应应返回汇总与明细分页：成功数量、已读跳过数量、失败数量、处理中数量及失败原因。

### 获取收件箱

`GET /api/internal-mail/inbox`

对于 `delivery_status=RECALLED` 的副本，只返回：

```json
{
  "id": "recipient-message-id",
  "recordType": "RECALLED_NOTICE",
  "senderName": "张建军",
  "subject": "张建军撤回了一封邮件",
  "summary": "该邮件已被发件人撤回，正文及附件不可查看。",
  "time": "2026-09-15 10:18",
  "availableActions": []
}
```

服务端不得向前端返回被撤回邮件的原始主题、正文、附件元数据或访问地址。

## 6. 并发、安全与异常

- 撤回接口必须幂等：同一邮件重复点击只返回同一任务或当前任务状态。
- 按收件人副本加乐观锁或条件更新，防止“正在阅读”与“正在撤回”竞争导致状态覆盖。
- 撤回处理过程中，读取接口以最终状态为准；无法确定时返回“处理中”，不可泄露内容。
- 附件下载、全文搜索、星标、缓存与索引均须同步撤销收件人对已撤回副本的内容访问。
- 权限校验在每一次正文、附件、预览请求中执行，不能只依赖前端隐藏按钮。
- 后端应记录失败原因，例如已读、外部地址、保留期已过、目标副本不存在、权限不足。

## 7. 验收清单

1. 未读内部收件人撤回后仅看到灰色系统提示，无法获取原内容。
2. 已读收件人原邮件不受影响。
3. 发件人能看到成功/失败汇总及收件人明细。
4. 已撤回副本不能通过搜索、附件 URL、浏览器缓存、星标列表或接口参数获取内容。
5. 重复撤回、并发阅读、部分失败、异步超时均有确定状态和可追溯日志。
6. 发件人删除已发送邮件不影响撤回审计与收件人侧最终状态。
